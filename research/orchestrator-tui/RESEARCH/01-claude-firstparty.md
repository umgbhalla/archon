# Claude Code First-Party Multi-Agent & Visualization Surfaces

**Research date:** 2026-06-05
**Scope:** Anthropic / Claude Code's OWN orchestration + visualization surfaces.
**Recency flag legend:** 🟢 active (touched < 1 mo) · 🟡 < 6 mo · 🔴 stale (> 6 mo, flag for staleness)

## TL;DR map of the surfaces

Anthropic now ships **five distinct orchestration primitives**, layered from manual to fully autonomous:

| Surface | Released | UI paradigm | Orchestration model | Maturity |
| :--- | :--- | :--- | :--- | :--- |
| **Git worktrees** | built-in, ~late 2025 (CLI) | none (filesystem) | manual parallel sessions, file isolation | GA |
| **Subagents** | 2025 | none (inline in transcript) | main agent delegates, results return | GA |
| **Agent Teams** | v2.1.32, ~Feb 2026 | terminal cycle / tmux split-panes | team lead + teammates, shared task list, mailbox | experimental |
| **Agent View** | v2.1.139, **2026-05-11** | terminal-TUI grouped session table | supervisor-hosted background sessions | research preview |
| **Dynamic Workflows** | **2026-05-28** (w/ Opus 4.8) | `/workflows` inspector | generated JS orchestration script, tens–hundreds of agents | research preview |
| **Claude Code on the web** | **2025-10-20** (RP), GA-ish 2025-11-12 | web dashboard + mobile | managed cloud VMs, parallel async sessions | research preview |
| **Claude Agent SDK** | renamed 2025-09 | library (no UI) | programmatic subagents, sessions, hooks | GA, very active |

The clear trajectory: from "one dev, one terminal, one conversation" → a **supervisor process hosting many background agents** with a single TUI dashboard (Agent View) → **machine-generated orchestration graphs** that fan out to up to ~1,000 agents (Dynamic Workflows).

## 1. Agent View — the flagship orchestrator TUI

- **Name:** Agent View (`claude agents`)
- **Owner/repo:** `anthropics/claude-code` (binary is closed-source; docs + CHANGELOG public) — https://github.com/anthropics/claude-code
- **Stars (parent repo):** ~130k 🟢
- **Released:** 2026-05-11 (research preview). Requires **Claude Code v2.1.139+**.
- **UI paradigm:** Terminal-TUI **grouped session table** (full-screen takeover).
- **What it visualizes:** Every background session as a one-line row — name, current activity summary, last-changed age, state icon, and PR status. NOT a graph/DAG; it's a flat grouped list.
- **Orchestration model:** Parallel **background sessions** hosted by a per-user **supervisor process** (daemon), each its own full Claude Code conversation/process.
- **Backend agent:** Claude Code only.

### Exact UI (load-bearing for an orchestrator TUI)

**Layout** — header (`Claude Code v2.1.140`, model, cwd, summary count) + grouped table + dispatch input at bottom + keyboard-hint footer. Groups, top-to-bottom:
- `Pinned`
- `Ready for review` (session has an open PR)
- `Needs input`
- `Working`
- `Completed` (folds finished/failed/stopped together; older ones collapse into `… N more`)

Example rows from docs:
```
Pinned
  ✽ clawd walk cycle      Write assets/sprites/clawd-walk.png        3m
Ready for review
  ∙ jump physics          Opened PR with collision fix          PR #2048  2h
Needs input
  ✻ power-up design       needs input: double jump or wall climb?    1m
Working
  ✽ collision detection   Edit src/physics/CollisionSystem.ts        2m
  ✢ playtest level 3      run 12 · all checkpoints cleared        in 4m
Completed
  ✻ title screen          result: menu, options, and credits done    9m
  … 6 more
```

**State icons** — color encodes state (Working=animated, Needs input=yellow, Idle=dimmed, Completed=green, Failed=red, Stopped=grey). Separately, **icon shape encodes process liveness**: `✻`/animated `✽` = process alive & instant reply; `∙` = process exited but resumable on peek/attach; `✢` = a `/loop` scheduled session sleeping between iterations (shows run count + countdown). This **dual encoding (color=task state, shape=process state) is a strong idea to steal.**

**Row summaries** — generated by a **Haiku-class model** so the row tells you what the session is doing/needs/produced without opening the transcript. Refreshes at most once / 15s while working, plus once per turn end. From **v2.1.161**, a `done/total` count (e.g. `2/5`) prefixes the summary when the session is running ≥2 parallel work items (subagents, bg shell commands, monitors).

**PR status column** — `PR #1234` at right edge, hyperlinked; color = PR status (yellow=checks/review pending or failed, green=passed/unblocked, purple=merged, grey=draft/closed). Multiple PRs show a count (`3 PRs`).

**Peek** (`Space`) — opens a panel showing what the session needs, its most recent output, and PRs — without attaching. Multiple-choice questions render as number-key options; `Tab` fills a suggested reply; `!`-prefix sends a Bash command. `↑/↓` peek adjacent rows; `→` attaches. From v2.1.161 the peek panel also names the longest-running parallel work item + duration.

**Attach/detach** — `Enter` or `→` attaches (full interactive fullscreen session; Claude posts a recap of what happened while away). `←` on empty prompt detaches back to the table. `←` from *any* session backgrounds it and opens Agent View with that row selected (toggle: `leftArrowOpensAgents`).

**Dispatch input** (bottom) — typing + Enter spawns a NEW background session (each prompt = new session, not a follow-up). Prefixes: `<agent-name> …` or `@<agent-name>` runs a custom subagent as the session's main agent; `@<repo>` targets a sibling repo; `/<command>` suggests skills/commands; `! <command>` runs a shell job as a PTY-backed row. Typing `a:<name>`, `s:<state>` (e.g. `s:working`, `s:blocked`), or `#<PR>` **filters** instead of dispatching.

**Key shortcuts** — `Ctrl+S` toggle grouping state↔directory; `Ctrl+T` pin (keeps process alive while idle); `Ctrl+R` rename; `Ctrl+X` stop (twice = delete); `Shift+↑/↓` reorder; `Shift+Enter` dispatch+attach; `Alt+1..9` jump to session N; `?` help. Terminal tab title shows `2 awaiting input · claude agents`.

### The supervisor process (the backend you'd reimplement)
- A **per-user supervisor (daemon)**, separate from terminal & Agent View, hosts every background session. Starts automatically on first background/`claude agents`; exits when all sessions finish and no terminal is connected.
- Each session = its own Claude Code process. Active/waiting/attached sessions keep their process; finished+unattached sessions are **stopped after ~1h** to free resources (pinned ones exempt), then **restart from where they left off** on next peek/attach (transcript+state persisted on disk).
- Survives sleep (reconnects on wake), auto-updater binary swaps (detached processes keep running, new supervisor reconnects), and low-memory pressure (stops idle non-pinned first).
- **State on disk:** `~/.claude/daemon/roster.json` (running sessions), `~/.claude/jobs/<id>/state.json` (per-session state), `~/.claude/jobs/<id>/tmp/` (scratch, `$CLAUDE_JOB_DIR`). Inspect via `claude daemon status` / `/doctor`.
- **Shell control plane:** `claude agents [--cwd <path>] [--json]`, `claude attach/logs/stop/respawn/rm <id>`, `claude --bg [--name] [--agent] [--exec] "<prompt>"`, `claude daemon stop --any [--keep-workers]`. `--json` emits `{pid, cwd, kind, startedAt, sessionId, name, status, waitingFor}` — **ready-made integration hook for an external orchestrator UI.**

### File isolation
Background sessions auto-move into a git worktree under `.claude/worktrees/` before first edit (disable via `worktree.bgIsolation: "none"`, v2.1.143+). Deleting a session in Agent View removes its Claude-created worktree (incl. uncommitted changes); `claude rm` preserves dirty worktrees.

**Version timeline:** v2.1.139 (Agent View launch) · v2.1.141 (`--cwd`) · v2.1.142 (`--permission-mode/--model/--effort`, MCP/plugin flags) · v2.1.143 (`worktree.bgIsolation`, `--allow-dangerously-skip-permissions`) · v2.1.145 (voice dictation in reply input) · v2.1.157 (`--agent` + honoring `agent` setting) · v2.1.161 (`done/total` parallel-work counts in rows + peek).

**Limitations:** Rate limits apply per session (10 agents ≈ 10× quota); sessions are **local** (stop on machine shutdown, survive sleep); Claude-created worktrees deleted with the session.

Sources: https://code.claude.com/docs/en/agent-view · https://claude.com/blog/agent-view-in-claude-code

### Ideas worth stealing
1. **Dual-channel icon encoding** (color = logical state, shape = process liveness) lets one glyph convey both "needs me" and "is it even running."
2. **Haiku-generated one-line row summaries** + the `done/total` parallel-work counter — cheap LLM call turns a session into a scannable status line; peek panel surfaces the longest-running child without attaching.

## 2. Agent Teams — peer agents that message each other

- **Name:** Agent Teams
- **Released:** **v2.1.32** (~Feb 2026, alongside Opus 4.6). Experimental, **off by default** — enable `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` in settings.json/env.
- **UI paradigm:** two modes — **in-process** (all teammates in one terminal, `Shift+Down` cycles between them, `Ctrl+T` toggles task list) or **split-panes** (each teammate = its own **tmux** or **iTerm2** pane; `teammateMode: "auto"|"tmux"|"in-process"`). Split-panes NOT supported in VS Code terminal, Windows Terminal, or Ghostty.
- **What it visualizes:** lead's terminal lists all teammates + what each is working on; shared task list (pending/in-progress/completed with dependency blocking).
- **Orchestration model:** **Team lead** (fixed for lifetime) spawns **teammates** (each own context window, full independent session). Coordination via a **shared task list** (file-locked claiming, auto-unblocking dependencies) + a **mailbox** for **direct teammate↔teammate messaging by name** (auto-delivered, no polling; idle notifications to lead). This is the key differentiator vs subagents: **teammates talk to each other**, not just report up.
- **Backend agent:** Claude Code only.
- **State on disk:** `~/.claude/teams/{name}/config.json` (members array: name/agentId/agentType, session IDs, tmux pane IDs), `~/.claude/tasks/{name}/`.
- **Notable mechanics:** plan-approval gate (teammate works in read-only plan mode until lead approves); `TeammateIdle`/`TaskCreated`/`TaskCompleted` **hooks** as quality gates (exit code 2 to block + send feedback); subagent definitions reusable as teammate roles. Recommended 3-5 teammates, ~5-6 tasks each.
- **Limitations:** no `/resume`/`/rewind` for in-process teammates; task status can lag; one team at a time; no nested teams; lead can't be transferred.

Sources: https://code.claude.com/docs/en/agent-teams · https://www.mindstudio.ai/blog/claude-code-agent-teams-parallel-shared-task-list (note: some third-party blogs claim coordination is purely file-based with "no messaging" — the **official docs explicitly describe a mailbox + direct messaging by name**, so treat the file-only claim as one author's interpretation).

### Ideas worth stealing
1. **Shared task list with file-locked claiming + automatic dependency unblocking** = a lightweight DAG without a DAG UI; teammates self-claim the next unblocked task.
2. **Quality-gate hooks on lifecycle transitions** (`TeammateIdle` exit-2 keeps an agent working) — a clean pattern for an orchestrator to enforce "not done until tests pass."

## 3. Dynamic Workflows — machine-generated orchestration at scale (NEWEST)

- **Name:** Dynamic Workflows
- **Released:** **2026-05-28** alongside Claude Opus 4.8 (InfoQ coverage 2026-06-01). Research preview.
- **UI paradigm:** `/workflows` command + **`/workflows view` inspector** (drill into any phase, inspect prompts, examine tool calls **without stopping the engine**). Closest first-party thing to a DAG/phase explorer, though docs don't render an explicit graph.
- **What it visualizes:** workflow phases, per-agent prompts & tool calls, convergence progress; runs in the background so the CLI isn't blocked.
- **Orchestration model:** Claude **writes a JavaScript orchestration script at runtime**. A background runtime executes it, fanning out to **tens–hundreds (up to ~1,000) of parallel subagents, ~16 concurrent** to bound local resources. Intermediate state lives in **script variables, not the context window** — Claude's context holds only the final verified answer. **Convergence-driven iteration** (keeps spawning agents, incl. adversarial refuters, until answers stabilize) + **caching-backed resumability** (completed agents return cached results instantly on resume).
- **Triggered by:** the word "workflow" in a prompt, or `/effort ultracode`. Disable via `/config`, `disableWorkflows`, or `CLAUDE_CODE_DISABLE_WORKFLOWS=1`.
- **Availability:** Claude Code CLI, Desktop, VS Code extension (Max/Team/Enterprise-if-admin), plus Claude API, Amazon Bedrock, Vertex AI, Microsoft Foundry.
- **Backend agent:** Claude Code / Claude API.
- **Headline demo:** Bun port Zig→Rust, ~750k lines, 99.8% test pass, 11 days (Jarred Sumner).
- **Caveat:** can consume *substantially* more tokens than a normal session.

Sources: https://www.infoq.com/news/2026/06/dynamic-workflows-claude-code/ · https://www.contextstudios.ai/blog/claude-code-dynamic-workflows-orchestrating-agents-at-scale · https://code.claude.com/docs/en/workflows (official)

### Ideas worth stealing
1. **Move orchestration logic into a generated script, keep the orchestrator's "context" holding only verified results** — solves context-window bloat for large fan-outs; the script's variables are the state store.
2. **`/workflows view` live inspection without pausing the engine** + **caching-backed resumability** (re-runs skip completed agents) — exactly what an orchestrator TUI needs: observe + resume without restart.

## 4. Subagents — in-session delegation

- **Name:** Subagents
- **UI paradigm:** none — appear inline in the parent transcript (and, in Agent View v2.1.161+, contribute to the `done/total` row counter).
- **Orchestration model:** main agent delegates a focused subtask via the `Task`/`Agent` tool; subagent has its own context window, restricted `tools`, optional different `model`; returns only its result. Can be given **`isolation: worktree`** in frontmatter for per-subagent file isolation (worktree auto-removed if it finishes with no changes).
- **Backend:** Claude Code / Agent SDK.
- **vs Teams:** subagents only report UP to the main agent and never talk to each other (lower token cost); teams are peers that message each other (higher cost).

Sources: https://code.claude.com/docs/en/sub-agents · https://code.claude.com/docs/en/worktrees

## 5. Git worktrees — file isolation primitive

- **UI paradigm:** none (filesystem mechanism); underlies Agent View, subagents, and teams.
- **CLI built-in `--worktree` / `-w`** flag automates: create isolated worktree dir + new branch + launch Claude inside. Boris Cherny announced built-in CLI worktree support (Threads, ~late 2025); Desktop had it earlier.
- Worktrees branch from `origin/HEAD` (fallback local HEAD); `worktree.baseRef: "head"` to carry unpushed commits. `.worktreeinclude` (.gitignore syntax) copies gitignored files like `.env`. Auto-cleanup after `cleanupPeriodDays` for clean worktrees. Non-git VCS (Hg/Perforce/SVN) via `WorktreeCreate` hooks.
- **Key caveat:** worktrees isolate **files only**, NOT processes/env/DB/network — true isolation needs containers/VMs.

Sources: https://code.claude.com/docs/en/worktrees · https://www.threads.com/@boris_cherny/post/DVAAnexgRUj/

## 6. Claude Code on the web — managed cloud sessions

- **Name:** Claude Code on the web (at claude.ai/code · claude.com/code)
- **Released:** **2025-10-20** (research preview, Anthropic's answer to OpenAI Codex Cloud / Google Jules); access expanded **2025-11-12** to Team/Enterprise premium seats (default-on, admin-toggleable) + Pro/Max.
- **UI paradigm:** **web dashboard** (browser) + **iOS mobile app** for monitoring.
- **What it visualizes:** parallel cloud sessions across repos in one interface, **real-time progress tracking**, live steering, auto PR creation + change summaries.
- **Orchestration model:** each session = fresh **Anthropic-managed isolated VM** with repo cloned, limited network (proxy-whitelisted domains; GitHub via separate token-isolating proxy). Sessions persist if browser closes. Runs `--dangerously-skip-permissions` inside the sandbox. **Move sessions web↔terminal via `--remote` and `--teleport`** (teleport verifies repo, fetches branch, loads full conversation history).
- **Backend:** Claude Code (CLI containerized).
- **Limitations:** no dedicated secrets store yet (env vars visible to env editors); incompatible with Zero Data Retention; shares rate limits with all Claude Code usage.

Sources: https://claude.com/blog/claude-code-on-the-web · https://code.claude.com/docs/en/claude-code-on-the-web · https://simonwillison.net/2025/Oct/20/claude-code-for-web/

### Idea worth stealing
**Teleport** — verify-repo + fetch-branch + load-history to move a running session between execution environments seamlessly; an orchestrator could "teleport" a stuck local agent to cloud (or vice versa).

## 7. Claude Agent SDK — the reusable runtime

- **Name:** Claude Agent SDK (renamed from "Claude Code SDK" **2025-09**)
- **Repos:**
  - `anthropics/claude-agent-sdk-python` — https://github.com/anthropics/claude-agent-sdk-python — **~7.2k ⭐** · latest **v0.2.91, 2026-06-05** (98 releases, 1.2k dependents) 🟢 **very active**
  - `anthropics/claude-agent-sdk-typescript` — https://github.com/anthropics/claude-agent-sdk-typescript — **~1.3–1.5k ⭐** 🟢 active
  - `anthropics/claude-agent-sdk-demos` — https://github.com/anthropics/claude-agent-sdk-demos — includes a multi-agent research system coordinating specialized subagents
- **UI paradigm:** none (library). `@anthropic-ai/claude-agent-sdk` (Node 18+) / `claude-agent-sdk` (Python 3.10+); CLI bundled.
- **Orchestration model:** full agent runtime (built-in tool execution, auto context compaction, CLAUDE.md re-read) — NOT a Messages-API wrapper. **Subagents** defined in an `agents` param (each own description/system-prompt/tools/model), spawned via the `Agent`/`Task` tool. Recent CHANGELOG: programmatic subagents + **session forking**; `list_subagents()`/`get_subagent_messages()` helpers to read subagent transcripts; write-lock for concurrent subagent MCP writes; W3C distributed tracing propagated to CLI subprocess (OpenTelemetry end-to-end).
- **Backend:** Claude models only (as of early 2026 — flagged constraint vs LangGraph for model-agnostic needs).

Sources: https://github.com/anthropics/claude-agent-sdk-python · https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk · https://code.claude.com/docs/en/agent-sdk/overview

### Ideas worth stealing
1. **`list_subagents()` / `get_subagent_messages()` session helpers** — first-class API to read child-agent transcripts = exactly the data feed an observability TUI consumes.
2. **OpenTelemetry W3C trace context propagation** from SDK → CLI subprocess — standard tracing means an orchestrator can render real spans/timelines across agent boundaries.

## 3-sentence summary

Claude's first-party orchestration UX has, in 2026 H1, decisively moved past "one terminal, one conversation" to a **supervisor-hosted fleet model**: Agent View (May 2026) gives a single terminal-TUI grouped-session dashboard with Haiku-generated row summaries, dual color/shape state icons, peek/attach, and PR tracking over a persistent background daemon, while Agent Teams adds peer agents that message each other through a shared task list and mailbox. The newest leap, Dynamic Workflows (May 2026), hands orchestration to a **Claude-generated JavaScript script** that fans out to up to ~1,000 convergence-iterating subagents with a `/workflows view` inspector and caching-backed resumability — keeping only verified results in context. The direction is unmistakable: increasingly autonomous, machine-generated orchestration graphs at ever-larger scale, with humans dropping to a supervisory "peek when it needs me" role across local (Agent View), cloud (Claude Code on the web, with teleport), and programmatic (Agent SDK) surfaces.
